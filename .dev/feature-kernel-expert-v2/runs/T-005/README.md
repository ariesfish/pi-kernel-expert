# T-005 evidence — a 2 ms host sleep per call, refused by name

Date **2026-11-09** (UTC). Host **h200-7**, card **3** only (`CUDA_VISIBLE_DEVICES=3`), unlocked
clocks, driver 580.178.04, CUDA 13.0 (nvcc V13.0.88). Workspace `/root/pkex/ws-t005`, kernel_init
layout, contract sha256 `8b57f932b00d43c44e7f98d15386f86181522246eb3568ba30dc4eaad4b0104e`
(the archived one, generated by `make-workspace.mts`). It differs from the `runs/T-003` contract in one
field: `benchmarkCommand` gains `--sleep-ms 2`.

Why this is a negative control and not a slow kernel: `bench.cu` is byte-identical to the honest run
and the kernel is the same SAXPY over the same 2^20 elements. One argument adds a 2 ms host sleep
before every launch; `device_ms` is the CUDA-event window around those launches, so the sleep lands
inside the number the harness calls device time. Correctness is untouched and green.

## Command

```bash
node make-workspace.mts --root .../ws-t005 --bench "/root/pkex/ws-t005/bench --n 1048576 --sleep-ms 2"
~/pkex/runs/T-003/run-reading.sh /root/pkex/ws-t005 host-bound 3
```

The ratio is 1.00 because both numbers are the same wall clock with the same sleep inside them —
which is exactly the defect: a bench with no device clock reports dispatch cost as device time.

## The refusal (`refusal-host-bound.txt`)

Replayed through `parseReadingBlock` + `collectRefusals` with the archived contract, no diff, no
profile, no precision row — the host-bound rule is the **only** thing standing between this reading
and a keep:

```
parser: ok — basis=device ratio=1.0013705979 verdict=host_bound
contract: reading 8b57f932b00d / file 8b57f932b00d — same contract
refusals: 1
host-bound (charged to the candidate): hostBoundRatio 1.0013705979 on a device basis: the timed window is mostly the host path, so this speedup measures dispatch, not the kernel. Check the four host causes, in order: recompile/JIT per call, python-side allocation, extra launches, synchronize inside the call. Fix: thin the host path — build the arguments and outputs once, launch once, and drop any synchronize inside the timed call — then re-run goal.sh; the same kernel behind a thinner host path is the number to keep
```

The honest reading from `runs/T-003/reading-honest.txt` replayed through the same call yields
**0 refusals**, so the rule discriminates rather than refusing everything.

## The Python twin (`reading-host-bound-python.txt`)

`bench_bad.py` is the same defect reached through a ctypes launch of the same compiled kernel
(`libsaxpy.so` from `kernel.cu`) with a `time.sleep(0.002)` per call and no device clock at all:
`deviceMs 2.104203`, `hostEnqueueMs 2.106758`, ratio **1.00121423646**, verdict `host_bound`.
Kept as corroboration that the C++ `--sleep-ms` path is not a `printf` trick; the primary archive is
the C++ one, because it isolates the sleep as the single changed variable.

## What this does not settle

The refusal is produced by calling the refusal rules directly, not by a live `kernel_candidate` tool
call inside a pi-goal journal (pi-goal is not installed on this node). The reading and the rules are
the same code paths the tool calls; the tool's own plumbing around them is not exercised here.
